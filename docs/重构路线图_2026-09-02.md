# 业财一体化 ERP 系统重构路线图

> 日期:2026-09-02 | 基线提交:`ddea05f`(A-K 需求全面对齐完成)
> 授权:用户全权委托,可重构/重写;技术栈固定 **FastAPI + Vue3 + Element Plus + MySQL 8.2**

## 一、系统现状盘点

- **模型(表)**:74 个(销售/财务/库存/采购/生产/质检/移库/审批/通知/附件/CRM/供应商)
- **后端**:19 个 router 文件,约 3 万行 Python
- **前端**:9 大模块 40+ 视图
- **已完成**:A-K 全部需求(发货尾款/询问式补货/超级角色/多财务/发票核验/颜色继承/全链看板/统计默认本月/移库)

## 二、问题清单

### 后端
1. **超大文件**:`inventory.py` 2361 行、`purchase_service.py` 2659 行、`sales_service.py` 1955 行、`analytics_service.py` 1869 行 —— 难以维护
2. **模型双入口**:根 `models.py`(真)与 `database/models.py`(死文件,已删)曾并存;`database.py` 是 DB 会话模块,命名与 `database/` 目录历史遗留易混淆
3. **错误处理不统一**:部分接口 `HTTPException(detail=dict)`(前端收不到 msg),部分 `api_response(code=409)` —— 需统一
4. **无自动化测试**:零 pytest,重构无安全网
5. **事务/竞态**:并发置货/发货有极小概率超卖(reserved 检查与扣减非原子)
6. 通知只写库,前端无红点/中心

### 前端
1. 页面风格不统一(表格/弹窗/筛选器各写各的)
2. 缺统一加载/空态/错误态
3. 移动端适配不完整
4. 无角色化首页看板(现有 DashboardView 偏数据)

## 三、重构优先级(按业务价值/风险比)

### P0. 测试安全网(先做,~半天)
- 安装 pytest + httpx
- 测试库:`yecai_test`(DATABASE_URL 环境变量切换),alembic 全量迁移 + 最小 seed
- 核心流程冒烟测试:登录→建单→审批→置货→补货→生产→质检→发货
- 关键业务规则断言:定金单尾款付清才能发货、询问式补货不自动生成、轮询分配等

### P1. 后端结构治理(~1天)
- 拆分超大 router:inventory.py → `inventory/{queues,transfers,stocks,demands,operations}.py`(保持 URL 不变)
- 抽公共层:`services/common.py`(统一错误响应/分页/序列化)
- 统一错误处理:全局 exception handler,业务错误一律 `api_response(code=409, msg=...)`
- 加类型注解(渐进式,新代码必须带)

### P2. 数据一致性加固(~半天)
- 置货/发货/移库扣库存:行级锁 `SELECT ... FOR UPDATE` 或原子 UPDATE 条件扣减
- 金额统一 Decimal 计算,入库转 float 仅序列化层

### P3. 前端体验统一(~1天)
- 公共组件:`DataTable`(加载/空态/错误态/分页)、`FilterBar`、`StatusTag`
- 页面批量迁移到公共组件
- 通知中心(红点 + 下拉列表 + 已读)
- 角色化首页看板

### P4. 业务增强(按需)
- 全链单据时间轴泳道图(后端 document_relations 已有)
- 消息通知接入(WebSocket 已有 realtime)
- 导出 Excel(销售/采购/库存/财务)

### P5. 工程化(~半天)
- pytest 接入 CI 脚本(Windows 一键跑)
- 部署脚本(启动/备份/恢复)
- README 重写(架构图/模块说明/测试账号)
